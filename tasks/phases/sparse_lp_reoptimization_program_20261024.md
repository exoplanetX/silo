## 1. 总目标与结束后的定位

在同一个SILO代码库中，形成**端到端稀疏、具备真实基更新和跨调用复用、能支撑中等规模
LP及连续修改实验的研究工具基线**。同时让现有MILP节点和一般RMP实际接入这一内核。
保留0.2.0a2稠密参考行为，开发伴学继续随大模块交付。

完成后预期达到“有明确支持域的基础研究工具”水平。这是本项目的评价用语，
不是行业认证；不等于工业竞争力、成熟商业求解器或新增科研贡献。
所有数字都是拟定验收目标，当前尚未运行这些规模/性能实验。

| 用户可见效果 | 必须实现的结果 | 评价边界 |
|---|---|---|
| 更大稀疏LP可求解 | 固定规模集覆盖最多2000变量、5000行、100000非零；指定必过模型均正确求解 | 不以超时/数值失败代替规模通过，不承诺任意此规模模型 |
| 连续修改确实更有效 | 8条固定轨迹的160个修改状态，warm/cold答案一致；真实跨调用因子复用、换基更新可定位 | 安全失效允许重分解/一次cold回退，不能每步cold冒充warm |
| 有可检验的重优化收益 | 5次成对计时；8条轨迹cold/warm比值中位数目标≥1.5，至少6条≥1 | 目标待验证；未达则性能目标未完成，不能宣称已经提速 |
| 稀疏性贯通全链 | A、变量变换、标准形、快照、原空间核验均不无条件展开全模型稠密矩阵 | 基LU填充和更新向量另计资源，不宣称全部工作量只随nnz线性增长 |
| 能服务现有上层 | 原MILP及一般CG在稀疏引擎下通过固定集成；保留界/gap、局部割、Phase I和全池核验 | 本轮不扩张MILP搜索算法或CG可声明的完整性范围 |
| 可安装、可复现 | 本地候选0.3.0a1，dense/sparse依赖配置及真实环境安装验证 | 发布、GitHub push、远端CI执行另按明确授权办理 |

本轮必须完成稀疏求解、更新复用、数值核验、上层接入、验证与文档；
不能只完成存储或稀疏LU接口便结束。完成第11节全部标准即停止。

## 2. 技术路线及依赖建议

**推荐：SILO自主单纯形/预处理/搜索算法 + 可选SciPy稀疏矩阵与SuperLU数值分解。**
基础安装继续NumPy/dense；建议新增`silo-solver[sparse]`，稀疏依赖按SP1实测组合锁定。
默认dense保持兼容；新增显式`SolveOptions(lp_engine="sparse")`及CLI对应参数。
首版不做自动引擎选择，避免缺包、规模门和默认行为的隐式变化。

稀疏路径只调用矩阵运算、LU及正/转置线性方程求解，不调用`scipy.optimize`、HiGHS或其他
优化算法。SILO仍决定Phase I/II、枢轴、基更新、预处理、状态、原始恢复和最优性。
调用数值分解库与调用外部优化求解器分开检查；core保持独立。
依赖、选项和快照兼容方案需在实施批准时纳入总合同，本提案不修改pyproject或运行时规则。

| 技术工作 | 具体设计要求 |
|---|---|
| 稀疏数据与变换 | 建立有限矩阵操作边界：行/列非零访问、A*x、A^T*y、abs(A)*abs(x)、加行列、抽取基；变量偏移/方向/拆分用索引映射，避免显式n×k变换T |
| 预处理与原空间核验 | 按非零支撑传播活动界，保留推导/恢复身份；KKT、Farkas及射线核验不先densify；容差职责和原始binary约定保持 |
| 稀疏标准形与基求解 | 稀疏追加slack/artificial；统一B及B^T求解；初始稀疏LU+SILO有界eta更新链；更新20次上限及残差触发重分解，安全阈值先冻结 |
| 更新正确性 | 分别核对正向与转置求解的更新顺序；逐步对照独立小矩阵解；不构造显式B逆；坏枢轴、近奇异、结构变化、填充/更新时间预算触发恢复 |
| 定价与数值处理 | 本轮选定Devex定价及确定性Bland回退；建立残差检查、最多2次迭代细化、受控重分解与现有cold回退；不同时加入多种竞争定价器 |
| 快照和会话 | 不可变语义basis快照与会话内部可变factor分开；版本化稀疏身份与系数验证，保留旧version2可检验导入/明确cold理由；无全模型dense tuple复制 |
| 四类重优化 | RHS、变量/行界、追加行、追加列均保持cold等值；RHS/基矩阵不变可保留factor，增行扩维允许重分解；缩放/预处理/固定自由域改变时严格失效 |
| MIP/RMP | 同一lp_engine贯通节点/局部割与Phase I/II增列；节点不共享可变搜索状态；不得通过上层强制dense规避稀疏验收 |
| 精确证明适配 | 精确基/GMI按需抽取受限对象，保留现有位数/维数/操作预算；允许小证明局部dense，不为大型模型全量dense；超限保守退出，不放松全池最优门 |
| 资源与诊断 | 分开记录输入/标准形nnz、LU的L/U非零、fill ratio、更新链字节、完整重分解和跨调用复用；稀疏规模门在dense分配前生效 |

主要受影响边界：`modeling/general.py`、`presolve/activity.py`、`lp/general.py`、
`lp/kernel.py`及数值实现、`lp/verification.py`、`lp/session.py`、`lp/tableau_view.py`、
`mip/general.py`和`decomposition/general_master.py`。
最终文件清单由总合同冻结；这些路径不是无关重构的许可。

阶段通过后在已批准合同内连续推进；函数、补丁、单测、伴学不另拆执行任务。
实际原子总任务上限1项；原计划必交付修复留在该合同，不自动追加后续合同。

所有输入ID、seed、原始/转换SHA、预期状态、真值、选项和组别在SP1一次冻结。
本规划先固定数量、来源选择及门槛；实际原始SHA须在取得文件后填写，不虚构哈希。
生成例采用固定seed20261024，配方在实现前提交；不按求解成绩选择种子。

| 数值与状态压力 | 24例：8可解退化/尺度/冗余、4不可行、4无界、4近奇异/依赖、4资源限额 | 前16例取得已知正确终态；4近奇异按事先声明的成功或保守退出集合，4限额按对应出口；后一组不能计作成功求解规模例 |
| 中等规模容量 | 12 LP，六类结构各2例，n≤2000、m≤5000、nnz≤100000；至少4例n,m均≥1000，至少1例同时达到2000变量/5000行 | **12/12必须正确求解**，每例≤120秒、进程峰值RSS≤1GiB；至少6例presolve=False且有≥20有效pivot、保持实质耦合，不能全靠separable捷径或复制行凑规模 |

### 外部实例与导入

固定Netlib ID为：AFIRO、ADLITTLE、BLEND、SC50A、SC50B、SC105、SC205、
SHARE2B、SCAGR7、SCFXM1、BANDM、DEGEN2。该选集用于从构造例过渡到外部LP，
不代表工业实例全集或现代benchmark排名。

Netlib包含压缩和标准MPS数据。验证工具可在独立导入层完成解码/转换，
不把全面fixed-column MPS公开支持追加成本轮产品目标。保存源URL、来源说明、原文件和
转换哈希、行列/非零数、目标常数/方向、变量界、RANGES映射；同时校核独立读入结果。
不得让SILO与比较器共同使用一个未经核对的转换，导致同源导入错误被当作一致性。

发布表中的最优数值可能为历史近似，不能把截断小数当精确真值；SP1冻结原数据上的
独立HiGHS解/对偶与原空间检查依据，分别注明证据精度。小型解析/有理oracle保持独立。
外部数据及运行输出进忽略目录，可重复下载脚本与小manifest入Git，不提交大数据或二进制。

## 5. 性能、数值和资源的硬判据

### 正确性优先

- 所有必过最优实例必须通过原模型的primal/dual/sign/complementarity/objective检查。
  默认容差保持0.2.0a2语义，不为个别实例放宽；目标对照阈值固定为
  `1e-7*(1+abs(reference))`，原空间核验使用既有预先定义的贡献尺度。
- 任一错误optimal/infeasible/unbounded是阻断缺陷，不能用其他实例通过率抵消。
- 压力组保守退出和资源限制单独计数；不纳入24个容量/外部必过例的成功数。
- 已修的F1–F4及1/3精确门必须保留；不把全部LP/MILP宣传为精确求解。

### 重优化与计时

- 同机、同进程策略、单线程、同版本及参数；首次导入/初始化单列报告。
  cold和warm交替顺序，5次固定重复。对每条轨迹分别计算cold总时间/warm总时间的中位数，
  再取8条比值中位数；目标≥1.5且至少6条比值≥1。
- 计时包含模型修改/复制、失效判断、规范化、基更新/分解、迭代和核验，不只截取三角求解。
  原始全部时间与比例都发布；最快一次不代表结果，失败/超时不删除。
- 对照同一新sparse引擎的逐状态cold重解，以隔离warm收益；旧dense参考在8个可承受重叠
  模型上另作定位比较，不对因资源门拒绝的dense结果计算虚构提速倍数。
- 任一轨迹快但无实际跨调用复用/更新依据，不能通过机制验收。
  达到机制线但未达时间线时，报告“机制完成、性能未达”，整个目标仍未全部完成。

### 内存与保护

- 无A、T、完整标准形或快照的无条件m*n/n*n稠密展开；允许基/证明预算内明确标记的
  小局部对象。用分配门禁与运行跟踪核对，不能仅从最终RSS猜测路径。
- 分别报告`nnz(A)`、`nnz(standard)`、`nnz(L)+nnz(U)`、更新链存储和峰值RSS。
  因子fill可高于输入稀疏度；设置因子非零与更新链预算，资源不足明确退出。
- RSS以独立进程OS峰值口径测量，不能以NumPy数组字节替代。外部hardwall/内存守护作为
  测试保护，若杀进程须记timeout/resource failure，不能伪装成solver正常返回limit。
  数值库单次调用的可中断性单独说明，进入/返回时检查deadline；不承诺Python能中断任意LU。

## 6. 各阶段审核、测试和评估怎样组织

每个门执行“开发主线程自检 → 必要只读独立复核 → 开发主线程登记门判定”。

通过后可继续，不为每个函数/补丁请求新许可。

| 检查点 | 审核重点 | 测试层次 | 决策 |
|---|---|---|---|
| SP1 | 数据语义、原符号/容差、依赖、eta及转置推导、失效规则、固定分母和预算 | 配方重建、原始/转换等值、真值/基线收据、环境与依赖可用性 | GO后冻结并实现；不具备则STOP，不能后选成功例 |

| SP3 | 更新顺序、残差恢复、缓存隔离、跨调用复用、计时公平 | 小矩阵逐步解 → 机制/失效 → 8条完整cold/warm轨迹 | 正确、机制与性能分别判定；三者都达线才GO |

发现重大数值错误先定位根因，只重跑受影响分组；不反复全量测试制造通过数。

## 7. 执行上限与失败处置

本规划建议**自动验证计算总预算8小时**，包含基线、失败、对照、构建安装及重试；
这是计算上限，不是对编码墙钟或交付日期的承诺，不设置未经用户指定的token预算。

| 预算桶 | 上限 |
|---|---|
| SP1设计/数据/基线检查 | 30分钟 |
| SP2稀疏cold及组件验证 | 60分钟 |
| SP3更新/重优化及机制验证 | 180分钟 |
| SP4集成、最终矩阵和安装 | 180分钟 |
| 集中修复/环境余量 | 30分钟 |
| 合计 | 480分钟 |

分桶上限可使用已声明余量，总预算不可自行增加。固定组运行可跨阶段复用收据，但源码
相关路径变更后须重核受影响组；不能把过期结果算作当前基线。

SP3最坏情况算术如下，正式轨迹最多两轮已包含，不依赖占用公共余量：

| SP3计算项 | 最大计算量 |
|---|---|
| 单轮正式轨迹 | 8条×2模式×5重复×60秒=80分钟 |
| 两轮正式轨迹 | 160分钟 |
| 8个机制例 | 8×60秒=8分钟 |
| 其余小矩阵、失效和静态检查合计 | 12分钟 |
| SP3上限 | 180分钟 |

单例上限和最多重跑数是保护界；全局/分桶余量不足时不得启动新的整轮，
也不承诺所有分组都能耗至各单例上限再重跑。达到预算而尚缺验收时保持未达，
不以“计划允许两轮”为理由自动延长480分钟。

- 每个阶段最多初验+两次针对性修正复核。容量/外部完整组全目标最多两轮。
- warm正式计时固定5重复/轮，完整轨迹组最多两轮。全部质量命令最多3轮，
  首次全量前先做静态lint和小组，避免纯格式错误导致昂贵重跑。
- 日常额外诊断最多20批、每批≤60秒；所有小运行记入时间和调用记录。
- 候选安装每组合一次；纯网络/锁文件环境故障允许同工件SHA一次重试，失败保持。
- 不采用128类混合的总solve调用上限：各组实例、配置、重复/轮次固定，记录真实总次数，
  同时执行总计算上限。单元测试内重复调用与正式基准分组标记清楚，不双记耗时或隐藏调用。
- 同一重大阻断两轮根因修正无进展、必要依赖/数据不可用、需改变目标/禁止范围、
  或预算耗尽时，交一个集中问题包并停止相关执行；未完成项继续登记未达。
  不自动追加轮次、改数据/阈值、扩大任务或把失败例移入允许失败组。
