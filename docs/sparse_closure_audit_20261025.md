## 2. 为什么反复报错和中断

### 2.1 已修复的真实算法问题

RR02后的实现先后发现并修复：严格最小比值筛主元导致可行稳定候选遗漏；Phase I清理
错误要求中间基对偶可行；dual退出的全局容差遮蔽原空间变量界；退化两步后长期Bland；
DEGEN2依赖行无法在原证明工作区内核验。它们解释了前期部分数值失败与工作量过大。
当前源码已有相应反例和固定组证据，不能继续把最新中断描述成SP2容量仍未解决。

### 2.2 验证和交付工具也出现了真实缺陷

历史汇总器将384条(id,config)记录误认为192条模型、把诊断recipe当64条结果；
uv安装没有写入所需archive SHA；Windows观察器与资源保护器共用ctypes函数对象并互改
`argtypes`；父子账本追加存在竞争窗口。这些问题均有失败记录和后续修补。
共同薄弱处是：有些工具只通过局部测试，缺少对真实冻结schema、实际安装器和真实并发
运行方式的端到端检查。测试很多仍不能自动覆盖未建模的交互。

warm4的附加Sampler报`expected LP_Entry instance instead of pointer to Entry`，0样本；
其线程CPU仅0.015625秒。资源guard在每个child中独立运行，全部80份monitor均保存正常退出、
空guard原因和root_and_descendants范围；若资源guard也抛出该ArgumentError，现有控制流
不会吞掉它并正常生成完整80份结果。因此缺少宿主trace不能推导其wall/RSS保护无效。

### 2.3 真实墙钟波动存在，唯一原因没有证明

同源warm3与warm5均75/80，失败是BOUND02 cold五次60秒OS超时；保存前缀的pivot/LU等
计数与成功轮对应路径一致。warm5的Sampler线程CPU为4.65625/659.758秒，约0.71%，
不支持单凭该观察器解释约两倍变慢。OneDrive及其他进程的忙碌是观测事实，唯一因果未证。

RR07两条cold均21/21正确，wall34.3699212/33.9672303秒、CPU34/33.6875秒。
wall相差约1.17%，而20核频率聚合相差10.1234%。该聚合未绑定求解实际运行核心，
10%阈值也未提供对原60秒目标的校准，因此不能用它证明求解器正确性或收益不足。
Windows会按性能与能耗进行处理器电源管理；频率本身并非固定常量。
参见[Microsoft处理器电源管理说明](https://learn.microsoft.com/en-us/windows-hardware/customize/power-settings/configure-processor-power-management-options)。

### 2.4 后加的辅助门逐步接管了原任务结束条件

RR04增加quiet及连续宿主观察，RR06处理观察器，RR07增加两cold≤45秒及频率≤10%。
用户确实批准了这些具体诊断/恢复包；执行者按各合同停止是合规的。
但它们没有改写01/02的原八项定义。将辅助观测HOLD直接等同于“原第4项没有达标证据”，
会让补充诊断不断成为新的前置条件。规划和监督方需要纠正这一证据角色混用。

另一个问题是以小额度逐次追加代替一次完整恢复方案。余额尚足，却重复等待新授权，
增加了中断和文档分叉。本次不再追加warm、probe或宿主实验；保留辅助包HOLD作为实际结果。
原总体/实施计划头部在最新执行之后仍写“SP2七轮后HOLD”，与当前总报告不一致；
一些镜像的“当前入口”仍首先指RR02。新对话可能据旧入口重复判断或准备已完成算法工作。
本次统一当前入口和摘要，历史流水留在报告及决策记录中。
